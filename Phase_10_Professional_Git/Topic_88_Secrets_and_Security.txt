============================================================
TOPIC 88 — SECRETS AND SECURITY
============================================================

1. WHAT IS A SECRET?
------------------------------------------------------------

A secret is sensitive information that should not be exposed.

Examples:

- API keys
- Passwords
- Access tokens
- Private keys
- Database credentials
- Cloud credentials
- Service account credentials


2. NEVER COMMIT SECRETS
------------------------------------------------------------

Do NOT put real credentials directly into Git.

Bad:

API_KEY=actual-secret-value

inside a tracked file.


3. USE ENVIRONMENT VARIABLES
------------------------------------------------------------

Applications can read secrets from environment variables.

Example:

API_KEY=<value supplied through environment>


4. .ENV FILES
------------------------------------------------------------

A local .env file may contain development secrets.

Example:

API_KEY=secret-value
DATABASE_PASSWORD=secret-value


The .env file should normally be excluded from Git.

Add it to:

.gitignore


Example:

.env
.env.local


5. .ENV.EXAMPLE
------------------------------------------------------------

A safe example file can document required variables.

Example:

.env.example

API_KEY=
DATABASE_URL=
DATABASE_PASSWORD=


Do not put real secrets in this file.


6. GITHUB SECRETS
------------------------------------------------------------

GitHub provides encrypted secrets that can be used by
workflows.

Example:

${{ secrets.API_KEY }}


7. SSH PRIVATE KEYS
------------------------------------------------------------

Private SSH keys must remain private.

Never commit:

id_rsa
id_ed25519
or other private key files.


8. IF A SECRET IS COMMITTED
------------------------------------------------------------

Deleting the file from the latest commit is not always
enough.

The secret may still exist in Git history.

The correct response normally includes:

1. Revoke or rotate the exposed secret.
2. Remove it from the repository.
3. Check whether it exists in history.
4. Rewrite history if necessary.
5. Force-push only when appropriate.
6. Notify affected systems/team members.


9. .GITIGNORE
------------------------------------------------------------

Use .gitignore to prevent common sensitive or local files
from being accidentally tracked.

Examples:

.env
*.pem
*.key
node_modules/
__pycache__/


10. SECRET SCANNING
------------------------------------------------------------

Repositories and CI systems can use secret-scanning tools
to detect accidentally committed credentials.


11. LEAST PRIVILEGE
------------------------------------------------------------

Give credentials only the permissions they actually need.

Example:

A deployment token should not automatically have access
to unrelated systems.


12. ROTATION
------------------------------------------------------------

Secrets should be rotated when necessary.

Especially rotate a credential if it has been exposed.


13. IMPORTANT SECURITY RULE
------------------------------------------------------------

A secret committed to Git should be considered exposed,
even if the commit is later deleted.


14. IMPORTANT MENTAL MODEL
------------------------------------------------------------

Git stores history.

Therefore:

"Delete the secret from the current file"

does NOT necessarily mean:

"The secret is gone from Git history."
